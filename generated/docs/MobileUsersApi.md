## batchLinkMobileUserToSides

> BatchLinkSidesResponse batchLinkMobileUserToSides(id, batchLinkSidesRequest, xCorrelationId, idempotencyKey)

Link one mobile user to many subscribers in a single call

The per-subscriber &#x60;POST /v1/sides/{sideId}/mobile-users&#x60; one call at a time: a console linking a whole search result would otherwise spend one request per row and exhaust the caller\&#39;s rate-limit budget. Repeated ids in &#x60;sideIds&#x60; are collapsed before anything is written. Pass &#x60;expectedCount&#x60; with the count the operator confirmed; when the distinct list is a different size nothing is written and 409 MOBILE_USER.BATCH_COUNT_MISMATCH comes back. At most 500 subscribers per call. A subscriber the user already has is counted in &#x60;alreadyLinkedCount&#x60;, not failed. A subscriber that cannot be linked — unknown, or in a monitoring center that would lock the user out — comes back in &#x60;failures[]&#x60; with its code rather than failing the call, so one bad row does not discard the rest.

## batchResetMobileUserPasswords

> BatchResetMobileUserPasswordsResponse batchResetMobileUserPasswords(batchResetMobileUserPasswordsRequest, xCorrelationId, idempotencyKey)

Give many mobile users a new generated password each and text it to them

Name the users by &#x60;mobileUserIds&#x60; (ticked rows) or by &#x60;filter&#x60; (the same &#x60;q&#x60; and &#x60;monitoringCenterId&#x60; the list takes), not both. At most 500 users per call. Pass &#x60;expectedCount&#x60; with the count the operator confirmed; when the resolved set is a different size nothing is written and 409 MOBILE_USER.RESET_COUNT_MISMATCH comes back. The server generates an 8-character password per user (lower-case letters and digits without look-alikes), stores only its hash and queues one SMS per user with &#x60;smsText&#x60;, where &#x60;{password}&#x60; (required), &#x60;{phone}&#x60; and &#x60;{name}&#x60; are filled in (case-insensitive). Without &#x60;smsText&#x60; the &#x60;mobilePasswordReset&#x60; SMS message template is used. The password is never returned. The SMS goes out through the monitoring center of one of the user\&#39;s subscribers — the requested centre when the user has one there. A user who cannot be texted (no subscriber, no phone, SMS over 250 characters) is reported in &#x60;failures[]&#x60; and keeps their old password. Password changes and SMS rows are written in one transaction.

## disableMobileUser

> MobileUserDetailResponse disableMobileUser(id, xCorrelationId, idempotencyKey)

Disable a mobile user

The user can no longer log in to the customer app, and every token already issued is refused within about 30 seconds. All devices are logged out and stop receiving push; the Firebase (realtime) session is revoked within about a minute and ends when its current ID token expires (at most 1 hour). Disabling a disabled user changes nothing.
